# `.ctf` conformance, Go implementation

This directory is an **independent second implementation** of the `.ctf`
container, written only from `ctf-format/spec/SPEC.md` and the files the spec
points at (`spec/generator.wit`, `spec/vectors/primitives.json`, and the
`spec/vectors/conformance/**` fixtures). It does not share code with, and was
not derived from, the Rust crates or the SDKs.

Module: `github.com/EinsBackstein/sidequests/ctf-format/go`
Toolchain: Go 1.27 (uses the standard-library `crypto/mlkem`, `crypto/mldsa`,
`crypto/hkdf`, and `crypto/ed25519`). SLH-DSA-SHA2-128s comes from
`github.com/cloudflare/circl/sign/slhdsa`; zstd from
`github.com/klauspost/compress/zstd`.

## Running it

```sh
cd ctf-format/go
gofmt -l .          # must print nothing
go vet ./...
go test ./...
```

`go test ./... -v` prints one line per conformance fixture and per primitive
vector, so a failure names the exact vector rather than a summary.

## What is implemented

### Container read path — complete

The §10 reader procedure, steps 1–8:

| Area | Rules |
|---|---|
| Header (§4) | H1–H14, including the H14-first ordering and `version_minor` left unvalidated |
| Section records (§5) | R1–R22 |
| Section table (§6) | T1–T8, including zero padding and `CONTAINER_V1` gating |
| Manifest (§7) | canonical CBOR decode/encode, M1–M25, `crit`, `paths`, `external` |
| Footer (§8) | F1–F10, commitment root, signature slot parsing and transcript |
| Chunk index (§9) | C1–C8, verified lazily on use, external streaming verification |

The parser never panics on hostile bytes and never sizes an allocation from an
unvalidated length: every length is checked against the file length, `MAX_SECTIONS`,
`MAX_CHUNK_SIZE`, or an overflow-safe product before use. Errors are `*ctf.Error`
with a category, a rule tag, and detail that contains only offsets, lengths,
indices and `name_id`s — never bytes echoed from the input.

### Compression — `comp = 1`

A `comp = 1` section is decompressed with `github.com/klauspost/compress/zstd`.
D1 (`MAX_DECOMPRESSED_SECTION`) and D2 (`MAX_DECOMPRESSION_RATIO`) are applied to
the authenticated table fields **before** the decoder is constructed (§5.4), and
the decoder is read through a bound of `len_plain + 1` so a hostile frame cannot
expand past its declaration. A decoder output that is not exactly `len_plain` is
rejected; the plaintext is then verified against `root`. An encrypted section
still needs its content key, and a compressed section whose kind this reader does
not implement is counted as unverifiable rather than decompressed (§10).


### Container write path — byte-identical to both goldens

`WriteBundle` reproduces the two committed golden files exactly, including
zero padding, 4096-byte payload alignment, record field order, canonical CBOR
key ordering, the footer, and the commitment root:

| Fixture | Bytes | SHA-256 |
|---|---:|---|
| `golden/minimal.ctf` | 4344 | `a23cd1b38496395bf42dfda95b4ceeac90a95f9662a2facc75ced433eafa3b36` |
| `golden/demo.ctf` | 18328 | `ce1a930e397964b68a3a0bde3b49a10c97b954dc63894f343166f12253016b36` |

These digests are printed by `go test ./ctf/ -run GoldenWrite -v`; the test
compares the generated bytes against the fixture with `bytes.Equal` before it
logs them. `TestMinimalGoldenParse` additionally parses the minimal fixture and
checks its commitment root and manifest; the conformance runner parses both
goldens.

The writer also emits `comp = 1` sections: one zstd frame per chunk when
`chunk_size != 0`, and a single frame when it is zero (§5.4). The default
(`Comp: 0`) path is unchanged, which is why the goldens stay byte-identical.

### Conformance vectors — all fixtures

`go test ./conformance/ -v` loads `spec/vectors/conformance/corpus.json` and
executes **all 35 listed fixtures** (`golden/`, `hostile/`, `future/`). It also
fails if any `.ctf` file on disk is not listed in the corpus, so a new fixture
cannot be silently skipped. Every result is logged, e.g.:

```
PASS accept golden-demo (18328 bytes, commitment ca81744b...)
PASS reject bad-magic: ctf: header: H2: bad file signature
PASS on-use reject compressed-ratio-cap: ctf: section: D2: ...
```

The corpus `expectation.kind` is honoured: `parses`, `parses_read_only`
(asserts `MayRewrite() == false`), `parses_unknown_optional` (asserts the
section exists, its kind is unimplemented, and it is not served), `rejects`,
`error`, `rejects_on_serve`, `serve_error`, and `chunk_index_error`.

### Primitives — 16 of 17 vectors plus round-trips

`go test ./vectors/ -v` executes every primitive vector that carries an
`expected` value from `spec/vectors/primitives.json`:

- 8 BLAKE3 hash vectors (lengths 0, 1, 3, 64, 1024, 1025, 4096, and `abc`)
- 4 HKDF-SHA256 vectors (RFC 5869 cases 1–3 and the crate-shaped case)
- 3 AEAD vectors (AES-256-GCM including empty plaintext, XChaCha20-Poly1305)
- 1 hybrid KEM vector (X25519 + ML-KEM-768, storage context)

The Ed25519 + ML-DSA-65 signature vector is **skipped**: its `expected` field
is empty and its reverse check was produced by the Rust crate, so it cannot be
used as an independent oracle without importing the implementation under test.
Round-trip tests instead cover Ed25519, ML-KEM-768, ML-DSA-65, SLH-DSA-SHA2-128s,
the hybrid signature for suites 1, 2, and 3, the hybrid KEM, AEAD-STREAM, key
envelopes and derived flags.

### Optional constructions (§18, §20–§22, §24)

Implemented and tested by round-trip:

- §20.1 hybrid KEM combiner and `ctf/kem/v1` transcript
- §20.2 AEAD-STREAM seal/open for suites 1 and 2, chunk AAD/framing
- §20.3 hybrid Ed25519 + ML-DSA-65 + SLH-DSA-SHA2-128s signing/verification,
  suite registry, footer transcript, signature slot lengths (suite 3's pq slot
  is `3309 + 7856 = 11165` bytes)
- §21 key envelopes and the `keys` section payload
- §22 derived seed, derived flag, stage key, and DF5 stage-gate rejection
- §24 sealed-progress payload (`SealProgress` / `Open`)
- §18 entitlement chain: canonical CBOR decode/encode, records, record ids,
  E1–E8 structural and chain validation, E9 verification against a §34 trust
  set, the §34.1 holder hash, and KD1–KD5 role separation

## What is not implemented

- Generator/solver execution (§23, §25), live gates, and the authoring front
  end.
- Section encryption is available through the primitives, and `SectionPlaintext`
  takes a content key, but encrypted sections are not opened end-to-end yet;
  there is no one-call "open this section from its envelope" helper.

## Layout

```
go/
  ctf/            container parser, writer, CBOR, manifest, chunk index, crypto
  conformance/    runner over spec/vectors/conformance/**
  vectors/        primitive vectors and crypto round-trips
  AMBIGUITIES.md  every place the spec allowed more than one reading, and the
                  reading chosen here
```

## Evidence for the byte-identity claim

The write tests are not weakened or golden-normalized; they compare raw bytes.
To reproduce the digest evidence:

```sh
cd ctf-format/go
go test ./ctf/ -run GoldenWrite -v
shasum -a 256 ../spec/vectors/conformance/golden/minimal.ctf \
               ../spec/vectors/conformance/golden/demo.ctf
```

The SHA-256 values logged by the test and printed by `sha256sum` are identical.
The test also logs BLAKE3 (minimal: `e4411ccb...b07fae`; demo:
`a8fd20c3...f19f0b`), which is the §11 file digest for the minimal bundle.
